# 事件与玩法配置

管理员入口：`/admin/events`。事件目录由 `lotteryd/api/events/catalog.go` 维护。

## 业务隔离

主站钩子只提交用户、业务编号和少量字段快照；不读规则、不计算概率、不等待奖励、不增加远程查询。独立有界队列由固定协程发送，超时后最多重试三次；满队列丢弃并计数，接收失败记录日志。事件不改变原接口的返回值、计费金额或任务结果。外层数据库事务中的业务钩子仅在提交成功后发送。

这是尽力投递：进程突然退出、队列满或接收端长时间不可用时可能漏事件。此设计优先保证原业务不等待、不因为玩法故障而失败，不承诺事件绝不丢失。不能将它用于决定本次请求是否放行、改变本次扣费或需要强一致的权益扣减。

主站需配置已有的 `lotteryd.grpc_addr` 与 `lotteryd.token`。事件接口强制要求非空内部令牌；与 lotteryd 的 `LOTTERYD_GRPC_TOKEN` 相同。保留旧充值奖励接口的行为。

`iqdetectd` 使用 `LOTTERYD_GRPC_ADDR`、`LOTTERYD_GRPC_TOKEN`，缺配置时不发送。mediad 复用既有 HMAC 签名回调，以 `gameplay.event` 发送小型事件；主站只接收固定媒体事件和字段白名单。

## 规则

同一事件可添加多条独立触发，每条分别配置筛选条件、概率、奖励对象、动作、次数、冷却及有效时间。新规则默认关闭。

- 概率用百万分比保存，0 永不命中，1,000,000 必定命中；页面输入百分数，支持四位小数。
- 多条规则独立判断，可以同时命中；不是加起来等于 100% 的奖池。
- 次数限制统计成功执行的次数；每日次数按处理当天的北京时间计算。
- 每 N 次按该用户收到并处理的此类事件累计判断，不能等同于规则创建后的第 N 次。
- 缺少筛选字段就不匹配；不从客户端补齐身份、金额或模型。
- 没有目标用户的系统事件不会给管理员自动发奖；可使用事件明确携带的邀请人、被邀请人或操作人。
- 规则停用、奖励总开关关闭时，已接收待执行事件也会跳过发奖。
- 事件接收时保存规则版本与道具效果快照，后续修改不改变已接收事件的判定参数。

## 动作与账目

支持发积分、发道具及调用已绑定的道具效果。道具可绑定积分奖励或道具奖励逻辑；调用效果时可选择消耗持有的道具。未实现的效果不会被当成执行成功。

接收事件先落库再确认。lotteryd 后台事务中处理事件、概率、次数与奖励：同一事件和同一触发只执行一次。概率来自服务端持久化密钥和事件、规则版本，不受投递重试影响。

每个动作使用独立保存点；动作失败不会撤回同一事件中其他动作已产生的奖励。执行记录区分条件不满足、未命中、次数受限、跳过、成功和失败。动作失败记录保留，不自动重新抽奖；数据库事务级失败会在后台重试，十次后标记失败。

积分奖励写入原积分流水，来源为 `event_reward`，并关联事件与触发编号。奖励本身默认不再产生新一轮玩法事件，防止奖励循环。道具奖励和效果执行在事件执行记录中保留数量、道具编号和结果。

## 累计与时间

首次、每日首次、连续活跃、Token/消费/充值/邀请累计、模型种类、连续调用结果及连续未中奖均由 lotteryd 处理。累计从事件接入时开始，不补算历史，也不把已有历史行为认定为从未发生。

注册天数使用已知注册时间；订阅、Key 即将到期使用接收到的有效期快照。时钟每分钟检查一次；未来 24 小时内的到期/活动时点可通过剩余秒数条件筛选，并用每日次数和冷却限制重复触发。未收到过有效期的旧权益不会被猜测或远程扫描。

消费阶梯在原有计算结果产生后发送观察快照，lotteryd 记录基线，只在之后观察到等级变化时派生事件。首次、累计等说明均以接入后收到的事件为准。

商城兑换、道具启用/到期、护盾等尚未实现的业务保留为“待接入”，不能配置可执行规则。页面获取、文件发送完成也不等同于用户认真阅读或保存成功。
